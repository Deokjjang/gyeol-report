## 2. 바꾼 것과 근거

### 2-1. 관측(1부) — migration 없음
호출마다 `book_generation_runs.calls`(와 Book meta.calls)에 남긴다: `stop`(stop_reason 원문) · `usage`(입력·캐시 읽기·캐시 쓰기·출력) · `maxTokens` · `sent`(보낸 thinking·effort) · `blocks`(블록 종류별 수·글자, 예 `{"thinking":{"n":1,"chars":0}}`) · `firstTextMs`(첫 본문 글자까지) · `thinkingTokens`(공급자가 줄 때만) · `stage`·`body`·`cls`. **생각 내용은 저장하지 않는다**(omitted라 0자, 크기만).
파일: src/lib/llm/{types,providers,streamCompletion}.ts, src/lib/writer/runner.ts(CallLog), src/lib/ops/generation/policy.ts(runSummary).

### 2-2. 출력 한도(2부 2)
- **1단 = 본문 추정 + 생각 여유 36,000**(종합 64,722 · 커리어 62,112 · 연애·궁합 61,183). 근거: 생각 소진이 쓴 양 = 운영 25,183~28,722(옛 한도 전부, 7회) · AM 36,365(잘린 값). 관측된 최대 소진량을 본문 위에 따로 얹었다. 문서의 「긴 작업 64,000부터」와 같은 크기.
- **2단 = 모델 상한 128,000**(문서). `MODEL_OUTPUT_CAP`의 64K 오기도 128K로 고쳤다.
- 둘 다 **남은 시간·주문 비용 상한 안에서만**(2-5·2-6). 생각 설정(between_tools, effort 기본 high)은 옛 코드와 같다 — 시험이 「두 호출 모두 between_tools·effort 없음」을 확인.

### 2-3. 생각 소진 분류(2부 3)
`stop_reason=max_tokens`(length)이고 본문이 비었거나 원한 장이 빠졌으면 「생각 소진」. 시간 초과로 끊겼는데 본문 0자이고 생각 블록이 있었어도 같은 것. 실패 분류는 생각 소진 · 연결(429·5xx·과부하·끊김) · 기타.

### 2-4. 이어 쓰기(2부 4)
- 끝까지 쓴 장(다음 장 머리글이 나온 장, 문단 1개 이상)은 받는 즉시 저장 — 원래 규칙 유지.
- 다음 호출은 **빠진 장만, 같은 생각 설정**. 문맥 = 브리프 전체(설계도) + **책 전체 장 목록** + **이미 쓴 장 원문**(옛 코드는 소제목·첫 80자 요약).
- 이어 쓴 책도 발행 전에 정리·결정론 검사·검수·수리·재검사를 책 전체에 다시 돈다(기존 흐름).
- 원문이 0자여도 그 호출 기록(stage·maxTokens·cls)이 남아 다음 시도가 1단을 되풀이하지 않는다.

### 2-5. 사다리(2부 5) — 품질을 낮추는 단계 없음
1단(본문 + 36,000) → 생각 소진이면 2단(모델 상한, 이어 쓰기 가능하면 빠진 장만) → 그래도 소진이면 더 부르지 않고 **보류 + 즉시 알림**.
- 같은 시도 안에서 2단을 부를 시간이 없으면 다음 시도(1분 뒤)가 2단부터. 단계는 지난 기록에서 정한다(옛 기록 length·0자는 「옛 한도 = 0단」으로 읽어 1단부터).
- **같은 호출 반복 금지**: 본문 0자로 소진한 같은 장 묶음을 다시 부를 때 한도가 그때의 1.1배를 넘지 못하면 부르지 않고 사다리 끝(`no_headroom`). 장을 쓰다 끊긴 뒤 빠진 장만 쓰는 이어 쓰기는 다른 호출이라 막지 않는다.

### 2-6. 주문 비용 상한(2부 6)
- **상한 = 정상 1권 비용 × 2.5, 작가 포함, 상품별**: 종합 $0.95 · 커리어 $0.90 · 연애 $0.85 · 궁합 $0.90(대운 $1.05·세운 $1.00). `ORDER_COST_CAP_USD`가 있으면 그 값.
- 「정상 1권 비용」 = 옛 작가 한도(본문 추정)를 끝까지 쓴 작가 1회 + 검수 + 수리 — 생각 소진 없이 끝나는 책이 들 수 있는 값(종합 0.05 + 0.287 + 0.04 ≈ $0.38 등). 운영 실측 완성 13권은 $0.19~0.27이다. **실측 중앙값 × 2.5($0.48~0.63)로 잡으면 1단이 옛 한도 + 5천 정도밖에 안 돼 여유를 줄 수 없어서** 이 기준을 골랐다(결정 필요 3).
- 한도를 부르기 전에 깎는다: 최악 비용(입력 전부 + 한도) ≤ 상한 − 지난 시도 비용 − **검수·수리 최악 몫($0.129)**. 깎은 값이 본문 추정보다 작으면 부르지 않고 보류(`cost_cap`) → 즉시 알림. 그래서 한 주문의 손실은 상한을 넘지 않는다.
- 진행 중인 주문도 다음 시도부터 같은 규칙(지난 시도 비용을 다 센다). 예: GR-6AA2는 이미 $1.55를 써서 새 코드에서는 더 부르지 않는다.
- 결과적으로 2.5배 안에서는 **1단 한 번이 사실상 전부**다(1단 소진 ≈ $0.53~0.71 뒤 남은 돈으로 본문을 못 씀). 2단은 1단이 시간·비용으로 작게 잘렸거나, 장을 쓰다 끊겨 빠진 장만 남았을 때 돈다.

2. **다시 만들기(만드는 중)**: 결제 큐가 다음 시도 대기(RETRYING·QUEUED)·보류여도, 비용 상한 안이면 다음 시도 시각을 지금으로 → 1분 크론이 다음 사다리 단계로 1회. 남은 상한이 정상 1권 비용보다 작으면 「비용 상한 — 환불 판단 필요(누적 $x / 상한 $y)」, 2단까지 소진이면 「생각 소진이 2단까지 — … 환불 판단 필요」를 버튼 알림으로 돌려준다. 환불 처리 중이면 거절. (이용권 책의 만드는 중 다시 만들기는 그대로 — 공개된 책만.)
3. **보류 즉시 알림**: 보류가 정해지는 그 시도에서 처리 봇으로 `⏸ 보류 — 환불 또는 대기 결정 필요 · GR-XXXX` + 사유 + 실패 한 줄 + 관리자 주문 화면 주소. 대기표 종류를 늘리면 migration이 필요해 처리 봇으로 바로 보낸다(버튼 없음 — 환불은 관리자 화면 또는 30분 알림의 버튼).
4. **자동 환불 시간**: 설정값 `AUTO_REFUND_HOURS`(1~72, 기본 **6시간**). 기한은 주문마다 저장하지 않고 `첫 실패 시각 + 설정값`으로 매번 계산 → **진행 중인 주문도 다음 판단부터 6시간을 따른다**(이미 24시간 기준으로 잡힌 다음 시도 시각은 그 시각에 깨어나 바로 판단). 보류도 이 기한까지만 두고(옛 30일), 기한이 지나 다시 잡히면 더 부르지 않고 포기 → 자동 환불(결제)·이용권 환급. 고객 화면 문구가 늘 맞게 하려는 것(원칙: 고객 대기에도 상한). 시간표: 1분·5분·15분·1시간·3시간 → 6시간째 마지막. 임시본(2시간)은 그대로.
5. **고객 지연 안내**(감독이 처음 시작한 지 15분 뒤에도 책이 없을 때, 만드는 중·평소보다 오래 화면):

6. **실패율 경보**: 같은 상품에서 1시간 안에 생각 소진이 **2건이 되는 순간**, 또는 그날(KST) 실패율이 **30%를 넘는 순간**(실패 3건 이상일 때) 처리 봇으로 「🚨 판매 일시 중지 검토 · 상품」. 판매는 멈추지 않는다. 상태를 저장하지 않고 「선을 막 넘을 때」만 보낸다.
