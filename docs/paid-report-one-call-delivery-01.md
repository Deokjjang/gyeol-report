# PAID-REPORT-ONE-CALL-DELIVERY-GUARANTEE-P0-01

## Delivery contract

`runPaidReportJob` is the paid orchestration entry. A durable claim increments `attempt_count` under the existing lease/row lock before generation. Only attempt 1 of a `run_number` may call the model; all other attempts are deterministic. Explicit authenticated admin retry starts a new run. No worker retry timing, payment, calendar, Dayun, evidence interpretation, price or retention policy changes.

| Product | Previous paid maximum HTTP calls per automatic cycle | New maximum |
|---|---:|---:|
| Comprehensive | 2 (one per first/second worker attempt; repair already disabled) | 1 |
| Career | 2 | 1 |
| Love/marriage/child | 2 | 1 |
| Compatibility | 4 (writer + repair in each of two attempts) | 1 |
| Major fortune | 2 | 1 |
| Annual fortune | 2 | 1 |

These are HTTP opportunities, a conservative ceiling on potentially billable calls. Timeout/unknown usage consumes the opportunity. Crash before HTTP also consumes it: prefer a complete fallback over uncertain rebilling. Existing leases/attempt uniqueness prevent concurrent claims; stale finishes cannot overwrite a newer publication. If storage fails after HTTP, the next claim uses fallback without HTTP. DB outages can still prevent delivery; this change does not promise completion while storage is unavailable.

Flow:

1. Normalize original paid input (annual purchase-time acceptance preserved).
2. Build canonical evidence and complete latest deterministic draft once, with writers disabled.
3. Run product validator, evidence/input/Bridge checks and new-publication gate. Invalid canonical input/evidence/fallback: no HTTP, retain paid order, attention.
4. Build existing product prompt/schema from that exact packet. Verify config/model syntax, existing 1 MiB serialized input guard and product output limit before transport. Missing config/oversized prompt: deliver already valid fallback without HTTP.
5. One Responses HTTP call, existing 120-second deadline. No application repair request, compatibility repair request or writer regeneration.
6. Validate raw facts before any attachments. If valid, keep model text. Narrow canonical rescue for allowed missing explanation/scene/internal presentation markers; revalidate. All other failures discard the model draft and return the complete prevalidated fallback immediately.
7. Independently gate again in the worker, persist snapshot in `finish_job` transaction. First successful publication starts the existing 90-day access period.

The old standalone product writers and repair helpers remain for their existing isolated tests/dev consumers. **Paid workers, the local paid harness and `/api/reports/create` use `generateProductReport`**, which never calls those repair helpers. The public create route remains unconditionally blocked in production.

## Rescue and contract closure

[Issue inventory](paid-one-call-validator-inventory.md) lists the six validators and shared publication/evidence dependencies, including dynamic-schema diagnostic families. Unknown codes and exceptions default to full fallback.

Medical/guaranteed claims are deliberately not cosmetically rewritten. Wrong pillars, MBTI facts, customer identity/direction, Dayun/year/month/segment, and unknown evidence IDs discard the draft. Immutable calculated fields are compared to the canonical draft before missing server-owned presentation attachments are added. Missing narratives are not silently populated to pretend a partial writer response succeeded.

Scene/explanation rescue replaces only the corresponding chapter/reading ID with its complete canonical counterpart. Marker rescue replaces only the matching presentation field. Both use the same customer's already validated evidence/draft. No new generic advice, numbered filler or theory is generated by repair. Existing validators are not weakened. These are structural/known semantic guards, not a claim that arbitrary natural-language hallucinations are perfectly decidable.

## Observability

Existing `external_calls` stores bounded model, input/output/total tokens, duration, sequence and outcome. New `delivery_audit` stores version, preflight, writer validation, rescue kinds, fallback, publish, failure code and code-only issues. Worker also strips raw suffixes from failure diagnostics before persistence. JSON parse failures and semantic validation failures stay distinct. A `validation` provider audit outcome means a response arrived but failed the application gate; `writerValidation` and `publish` disambiguate final delivery.

Only allowlisted scalar/code metadata is stored. No prompt/response body, authorization, user input, raw provider message or unrestricted diagnostics. A crash/expired lease can leave an unfinished/abandoned attempt with no recorded usage: **unknown, not zero cost**. Its first writer opportunity is still consumed. Successful fallback does not increment model calls or wait for another network deadline.

## Local paid QA

`POST /api/dev/paid-report-qa` accepts the normal report payload. It runs **the real `runPaidReportJob` and `generateProductReport`**, substitutes an in-memory claim/finish store, and saves to the existing shared `preview_memory` adapter. Returned `url` is the actual `/reports/{reportId}` customer page. Tests exercise all six products through this page, including read/re-entry without generation.

Required local process settings: NODE_ENV development/test, REPORT_PERSISTENCE_MODE preview_memory, PAID_REPORT_RELIABILITY_ENABLED not 1. Production/other environments always return generic 404 before body parsing/runtime secret resolution, regardless of preview flags. The harness never imports a Toss client or instantiates a Supabase store. Explicit local preview result reads do not fall through to durable/legacy Supabase reads, including missing IDs.

Next real QA must be separately authorized. Start the ordinary local server with these process settings, then submit one authorized synthetic fixture to this endpoint, inspect allowlisted `diagnostic`, and open returned customer URL. No browser data entry, no payment, no worker cron trigger. Each explicit harness POST is a new local run; do not manually repeat it merely because the model failed. Memory snapshots disappear on process restart; this is not a durability test.
