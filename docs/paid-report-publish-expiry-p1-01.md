# Paid report publication expiry

## Policy audit

| Data/purpose | Existing SSOT | Implementation after this patch |
| --- | --- | --- |
| Online access | `termsPolicy.ts`, 상품 및 제공 방식: 생성일로부터 90일 | First successful gated publication + 90 absolute days |
| Report result, including personal data | `privacyPolicyRetentionRows`, 리포트 결과: 리포트 생성일로부터 90일 | Same first-publication deadline; expired reads immediately hide content; worker clears snapshot |
| Report input | `privacyPolicyRetentionRows`, 리포트 입력정보: 리포트 생성일로부터 90일 | First publication sets the input deadline in the same transaction; JSON payload/annual acceptance unchanged |
| Payment/contract/dispute | `privacyPolicyLegalRetentionKo`, 별도 법정 보관 | Existing financial rows retained; no new legal duration is invented |

The two privacy rows independently specify the same generation-based period; input is not changed merely because access is changed. No legal copy changes are made. Refund/terms provide regeneration or refund for non-delivery/system fault but do not specify a new 90-day term after a previously published report is corrected.

Before any successful publication, input still uses the existing provisional 90-day retention (from preparation, reset on first payment confirmation). This preserves the existing bounded handling of abandoned inputs. The exact business retention limit for never-delivered paid orders is not explicit in the policy and needs a separate decision. This patch does not silently retain those inputs forever. If that deadline is exhausted, cleanup removes input/attempt validation details, keeps PAID, and marks unpublished fulfillment `FAILED_REQUIRES_ATTENTION` with `INPUT_RETENTION_EXPIRED`. There was never a report access countdown. Admin retry cannot reconstruct deleted input; operations must investigate/reprovide or refund under the existing non-delivery policy.

## Root cause and first publication

Previously, report `expires_at` defaulted to row creation +90 days, before generation. `finish_job` only wrote `published_at`, including overwriting it on corrected publication. Input expiry started from payment. Delayed fulfillment therefore reduced both access and input availability relative to the stated generation-based term.

The new SQL patch:

- Removes only the paid report `expires_at` default and NOT NULL constraint. Unpublished report rows have NULL `published_at` and `expires_at`.
- Adds a validated constraint: COMPLETED cannot lack publication/expiry; an existing publication has exactly publication +2160 hours of access. Using hours preserves 90 absolute days even if another DB session uses a DST timezone.
- In the successful `finish_job` transaction, sets the first DB `clock_timestamp()`, report expiry, input expiry, and snapshot `createdAtIso` together. Client dates and original queued-row creation cannot determine the displayed generation date or access deadline.
- Retains the first publication/deadline on quarantine and corrected republication. No automatic shortening, resetting or compensatory extension.
- Allows claim/admin retry for unpublished rows with NULL access expiry. Existing lease, attempt count/backoff, annual acceptance, recovery queue and financial transitions are preserved.
- Keeps `read_report` pure; at the exact deadline it returns EXPIRED with no snapshot. Cleanup clears expired published content even if it is currently quarantined or undergoing recovery.
- Scrubs attempt validation details at published expiry or exhaustion of unpublished input retention. Financial and non-PII audit identifiers remain.

Publication locks the input row and checks it has not already expired. Cleanup skips job rows locked by a finishing publication and uses input-before-attempt lock order. It never recreates deleted inputs. The app publish gate still runs before the internal successful finish call; SQL additionally requires its existing gate version, snapshot shape and report/product identity.

## Reads and sharing

The current `ReportShareActions` shares the same `/reports/{reportId}` URL. That page uses `readPublishedReport` and the durable `read_report` RPC, with no created-at-based secondary expiry calculation. The snapshot generation date is now overwritten by the publication transaction. The page remains dynamic and the expired UX is unchanged.

Legacy `/r/{token}` uses legacy `reports` storage and is not migrated or converted by this patch. It is not the URL generated by the current durable report share action. No new claim about legacy retention is made here.

5. Separately approved application deployment.

Do not reapply an older RPC patch after step 3 without reapplying the latest patch. Do not use db push or migration repair. The historical reconciliation postflight verifies the old non-null +90-day report default and is not the expiry postflight for this release.

The user supplied a previous audit reporting zero durable snapshots; this task does not query production. The patch uses a short lock timeout and transaction. Existing rows with incompatible report or published-input deadlines cause `EXISTING_REPORT_EXPIRY_REVIEW_REQUIRED` and rollback, including DDL. No backfill, row deletion, legacy conversion or guessed first-publication timestamp occurs during patch application. Compatible populated storage supports safe reapplication.

## Decisions still needed

- Whether already-delivered customers receive a compensatory extension following quarantine/regeneration. Current automation preserves the original first-publication term.
- The explicit retention/CS disposition deadline for a paid order that has never produced a valid report. Existing provisional input retention is preserved pending that decision.
- Exact legal-record retention/operational deletion rules remain a separate existing policy/operations concern; this patch deliberately does not assign new durations.
